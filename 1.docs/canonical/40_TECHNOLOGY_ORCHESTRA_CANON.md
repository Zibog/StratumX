# Technology Orchestra Canon

**Stack version:** `SX-CANON/1.0.28/STACK-v34`

## Purpose
Freeze the root doctrine that makes the stack read as one governed technology system rather than a pile of strong domain documents.
This file is not a theme document. It is the top orchestration law for how truth, mutation, publication, diagnostics, persistence, validation, and degraded posture are coordinated across physics, graphics, audio, world, gameplay, tooling, SDK, and editor.

## Root reading law
The stack must be readable in this order whenever a new capability, bug, denial, or proof obligation is introduced:
1. root doctrine defines the orchestration law and the mandatory chain;
2. domain canon defines the owned truth and downstream consequence law;
3. editor/tooling/SDK define operator access, packetized mutation, and visible diagnostics;
4. evidence and readiness matrices state whether the route is active, freeze-relevant, or still implementation-open.

No lower document may silently weaken the orchestration law by being more specific.
If a lower document is richer than root, root must be expanded until the richer domain can still be read from root without semantic gaps.

## Mandatory orchestration chain
Every active route in the stack must be explainable through the same backbone:

`declared truth -> lawful mutation ingress -> owned processing -> consequence publication -> operator-visible diagnostics -> compare/capture -> save/restore -> freeze/build/export/launch`

This chain is mandatory for all domains, including “simple” ones.
There are no exception domains that may mutate truth directly, publish hidden side-effects, or skip diagnostics because they are “editor-only”, “runtime-only”, or “just a preview”.

## Truth and mutation law
- Root owns the doctrine that truth is declared, typed, and package-owned.
- Engine owns runtime truth and consequence evaluation.
- SDK owns transport vocabulary, schema, and compatibility law.
- Tooling owns orchestration helpers, validation relays, and artifact pipelines.
- Editor owns operator surfaces, focus rules, compare/capture entry, and deny visibility.
- World docs own disk identity and restore-safe package layout.

No document may invent a hidden truth store.
No document may allow a top-layer direct mutation of engine truth.
No domain may hide derived caches or projections as if they were authority.

## Consequence lattice law
Every authored or runtime mutation must declare both its immediate owned result and its downstream consequence families.
At minimum, the stack must treat the following as first-class cross-domain publications:
- physical consequence;
- material consequence;
- graphics consequence;
- audio consequence;
- navigation/traversal consequence;
- persistence consequence;
- validation consequence;
- degrade/fallback consequence.

A domain is not closed if it only describes its solve or internal update.
It is closed only when the downstream publications are frozen and auditable.

## Budget and degraded posture law
Budget is orchestration, not a per-domain afterthought.
Every major route must declare:
- hot-path owner;
- visible degrade ladder;
- first denied action when the ladder bottoms out;
- artifacts retained for compare against the last-good rung;
- whether the degraded result is still lawful for certification, authoring, simulation, or release.

Graphics, audio, world streaming, and physics tiering may use different degrade mechanisms, but they must all publish them through one operator-visible doctrine.
“Looks worse”, “sounds thinner”, or “simulates cheaper” are not enough. The operator must see which rung changed and why.

## Root obligations for major product routes
### Project to playable product
Root must provide one readable conveyor from project bootstrap to launched build.
That conveyor must include world identity, material-first authoring, simulation, diagnostics, save/restore, and release proof.

### World authoring and validation
Root must make world-family docs read as one package law: identity, chunk invalidation, streaming profile, material linkage, persistence, validation, and degraded posture.

### Simulate, fix, freeze
Root must force every simulate/fix loop to preserve baseline lineage, first blocker visibility, and one explicit legal recovery action.

### Frame and sound delivery
Root must govern the frame-to-screen and sound-to-speaker chains as orchestration-grade chains, not just domain summaries.

## Forbidden shortcuts
- No domain-specific canon may bypass root orchestration by declaring local direct-to-runtime mutation.
- No product route may jump from “looks okay” to freeze/build/export without compare, evidence, and restore-safe baselines.
- No world save may persist unresolved chunk invalidation, unresolved material linkage, or ambiguous identity namespaces.
- No frame or sound chain may end in “failed/quiet/black” without a first boundary diagnosis.
- No old-floor claim may rely on vibes; it must cite the degrade ladder and retained evidence bundle.

## Closure standard
Root orchestra closure is accepted only when a strict reader can answer all of the following from root without guessing:
- where truth lives;
- how it is mutated lawfully;
- what downstream consequence families must publish;
- how the operator sees denial, degradation, compare, and recovery;
- what world/save/release identities must remain stable.


## Base-shell promoted route doctrine
Root orchestration must know promoted base-shell controls no worse than heavy labs.
Therefore the following are orchestration-grade routes, not mere menu cosmetics:
- project/world open/save/validate;
- terrain import/sculpt/smooth/flatten/paint/rebuild/save;
- material assign/bind/preview/save;
- sky bind/set/bind-cloud;
- shell surface activation and context restore;
- advanced everyday audio authoring for placed sources, zones, policies, and audibility preview.

For those routes root doctrine requires:
- one command grammar entry;
- one schema-field set sufficient for validation and publication;
- one denial family;
- one focus law;
- one evidence law whenever truth mutates or validation produces a retained verdict.

## Implementation-tail doctrine
A mutating command is not closed merely because its label and route exist.
Root closure requires explicit answers to:
- what authoritative truth changes;
- which validation gates run;
- which derived caches and indices invalidate;
- what viewport and shell publications happen immediately;
- what is saved now versus marked pending;
- which recovery anchor exists;
- which denial family returns on failure.
