# Document Role And Authority Discipline Canon

**Stack version:** `SX-CANON/1.0.28/STACK-v34`

## Purpose
Make it impossible for one file to pretend it is a constitution, manual, catalog, route, lab, and status ledger at the same time.

## Role law
| Role | Must contain | Must not fake |
|---|---|---|
| constitution | owners, state carriers, update/order, failure classes, publications, companions, proof duties | vague prose with no exact obligations |
| manual | stitched reading order, package companions, why the band exists | primary ownership of runtime truth |
| catalog | field or surface inventory, compatibility notes, consumers | mutation law |
| routing canon | exact stages, blockers, recovery, artifacts, focus return | runtime truth ownership |
| operator lab | windows, buttons, controls, overlays, inspectors, disabled reasons, captures | silent backend assumptions |
| registry | canonical names/ids/families | process narration |
| matrix | pass/partial/fail accounting | hidden authority |
| ledger | honest present-tense status | flattering closure claims without evidence |
| playbook | ordered operator steps and expected result | generic architecture summary |

## Authority rule
One ordinal owns one role.
A companion file may elaborate, but it must sit on a different ordinal.

## Naming rule
Document names must reveal role directly through one of the approved suffix families:
- `CONSTITUTION_CANON`
- `MANUAL_CANON`
- `CATALOG`
- `ROUTING_CANON`
- `LAB_CANON`
- `REGISTRY`
- `MATRIX`
- `LEDGER`
- `PLAYBOOK_CANON`

## Thin-closure rule
A file may not claim execution-grade status unless it contains at least the mandatory fields for its role.
If that minimum is absent, the file is a sketch and must be either thickened, renamed, or demoted.
